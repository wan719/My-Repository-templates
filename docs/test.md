# 软件测试规范（Test Strategy）

> 本文档用于规范项目的软件测试活动，为开发者和 AI Agent 提供统一的测试执行依据。
>
> 核心原则：**测试左移、风险驱动、自动化优先、持续反馈、按需扩展。**

## 1. 测试原则与职责

### 1.1 基本原则

1. **测试左移**：需求分析和功能设计阶段就明确验收条件，不等到编码结束后才考虑测试。
2. **风险驱动**：根据功能重要性、变更影响范围和失败后果决定测试深度。
3. **自动化优先**：能够稳定自动执行的重复性测试，优先纳入自动化流程。
4. **持续反馈**：尽早发现缺陷，避免问题积累到集成或部署阶段。
5. **按需扩展**：不追求测试种类齐全，而是选择对当前项目真正有价值的测试。

### 1.2 职责划分

**开发者负责：**

- 确定功能需求、验收标准和质量目标。
- 审核重要测试策略与高风险测试用例。
- 判断测试结果是否满足实际需求。
- 决定已知风险是否可以接受。

**AI Agent 负责：**

- 分析代码变更及潜在影响。
- 根据要求设计和编写自动化测试。
- 执行授权范围内的测试、分析失败原因。
- 修复缺陷并运行必要的回归测试。
- 汇报测试结果、覆盖范围和剩余风险。

**CI/CD 负责：**

- 在预设事件发生时自动执行测试。
- 保存测试结果并反馈失败信息。
- 根据质量门禁决定是否允许合并或部署。

Agent 执行测试不代表开发者放弃质量责任。

## 2. 测试策略

根据项目规模和风险选择测试，不强制执行所有测试类型。

### 2.1 单元测试（基础测试）

**适用对象：**

- 核心业务逻辑。
- 算法和数据处理逻辑。
- 具有分支、边界条件的业务方法。
- 缺陷修复涉及的代码。

**基本要求：**

- 覆盖正常输入、边界情况和典型异常。
- 使用有意义的断言验证实际行为。
- 对外部依赖按需使用 Mock。
- 保持测试独立、可重复、运行速度较快。

Java 项目可优先使用 JUnit 5、Mockito。

### 2.2 集成测试（按依赖触发）

当代码涉及以下内容时，应考虑编写集成测试：

- 数据库读写及事务。
- 模块间协作。
- REST API 与服务端组件集成。
- 微服务接口调用与契约变更。
- 消息队列、缓存和外部服务。

**基本要求：**

- 重点验证组件之间的真实协作。
- 必要时使用隔离的测试数据库或 Testcontainers。
- 不使用 Mock 替代所有关键集成行为。
- 根据实际架构选择集成测试策略，不强制采用固定的集成顺序。

### 2.3 系统测试（按风险选择）

根据项目实际情况选择：

| 测试类型  | 触发条件                |
| ----- | ------------------- |
| 功能测试  | 新增功能、重要功能变更         |
| 性能测试  | 存在性能目标、性能瓶颈或高负载风险   |
| 安全性测试 | 涉及认证、授权、敏感数据及其他安全风险 |
| 兼容性测试 | 需要支持多个平台、浏览器或运行环境   |
| 可靠性测试 | 涉及高可用、容错、恢复等要求      |
| 易用性测试 | 用户交互体验是重要验收目标       |

对于普通项目，优先保障核心业务流程。

### 2.4 回归测试（持续执行）

以下情况应执行与变更影响范围匹配的回归测试：

- 修复已有缺陷。
- 修改已有功能。
- 重构核心模块。
- 升级重要依赖。
- 修改公共接口或数据结构。

每个可复现的缺陷原则上都应增加对应的回归测试，避免同类问题再次出现。

## 3. 测试工具与环境

测试工具根据项目实际技术栈选择，禁止为满足本模板而引入不必要的依赖。

**Java/Spring Boot 项目参考：**

| 工具                         | 用途               |
| -------------------------- | ---------------- |
| JUnit 5                    | 单元测试与集成测试        |
| Mockito                    | 模拟外部依赖           |
| JaCoCo                     | 代码覆盖率分析          |
| Spring Boot Test           | Spring 组件及应用集成测试 |
| Testcontainers             | 按需提供隔离的真实依赖环境    |
| Maven / Gradle             | 测试构建与执行          |
| GitHub Actions / GitLab CI | 持续集成与自动测试        |

**环境要求：**

- 测试不得依赖生产环境中的真实业务数据。
- 测试应尽可能独立、可重复。
- 外部依赖必须明确其运行条件。
- 测试配置、依赖版本和执行命令以项目实际配置为准。
- 不得仅为让测试通过而随意降低断言要求。

项目初始化时，应在此处补充实际使用的测试工具、测试目录和运行命令。

## 4. 测试执行流程

### 4.1 需求与设计阶段

开发新功能前：

1. 明确功能的预期行为和验收标准。
2. 识别关键边界条件、异常路径和潜在风险。
3. 确定必要的测试类型。

### 4.2 编码阶段

开发过程中：

1. Agent 根据需求编写或更新必要的测试。
2. 完成功能后执行直接相关的测试。
3. 测试失败时分析根因并修复。
4. 缺陷修复后执行相关回归测试。

对于适合测试驱动开发的模块，可以先编写失败测试，再实现功能。

### 4.3 提交与合并阶段

根据实际 CI/CD 配置，建议采用：

| 时机           | 默认测试要求              |
| ------------ | ------------------- |
| 开发过程中        | 变更相关的快速测试           |
| Pull Request | 构建检查、单元测试、必要的集成测试   |
| 合并主分支前       | 检查测试结果和质量门禁         |
| 部署前          | 核心业务流程验证及按风险选择的专项测试 |

对于运行成本较高的测试，可按需安排在定时任务或特定流水线中，不必每次提交都执行。

## 5. 质量门禁

### 5.1 基础通过标准

原则上，代码合并前应满足：

- 项目构建成功。
- 本次变更涉及的必要测试通过。
- 没有未经处理的新引入测试失败。
- 关键业务需求具有相应验证证据。
- 测试失败、跳过或无法执行的情况已明确说明。

未执行的测试不得报告为通过。

### 5.2 覆盖率要求

使用覆盖率工具辅助发现测试盲区，但不将覆盖率等同于软件质量。

初期不设置统一的强制覆盖率百分比。

优先关注：

- 核心业务逻辑是否有测试。
- 重要条件分支是否经过验证。
- 已修复缺陷是否有回归测试。
- 新增高风险代码是否存在明显测试缺口。

后续可以根据项目实测基线建立合理的覆盖率目标。

### 5.3 测试失败处理

测试失败时：

1. 保留错误日志和复现条件。
2. 判断是业务缺陷、测试代码问题还是环境问题。
3. 修复根本原因。
4. 重新执行失败测试及必要的回归测试。
5. 记录尚未解决的问题。

不得通过删除测试、禁用断言或伪造结果来满足质量门禁。

## 6. Agent 测试执行规范

### 6.1 执行前

Agent 应当：

1. 阅读本规范及项目相关说明。
2. 检查项目实际技术栈、测试框架和运行命令。
3. 分析本次代码变更的影响范围。
4. 选择与风险匹配的测试，不盲目执行全部测试。
5. 识别测试所需环境和权限。

### 6.2 执行中

Agent 应当：

- 编写具有实际验证价值的测试。
- 优先验证外部可观察行为，而非仅验证内部实现细节。
- 对重要逻辑考虑异常、边界和失败路径。
- 必要时运行集成测试验证真实依赖。
- 对测试失败进行根因分析。
- 未经授权不得修改生产数据、执行破坏性操作或扩大执行范围。

### 6.3 执行后

Agent 必须给出简要测试报告：

**测试报告模板**

- **变更内容**：本次完成的功能或修改。
- **测试范围**：执行了哪些测试，覆盖什么行为。
- **执行结果**：通过、失败、跳过或未执行。
- **覆盖率**：如已生成报告，则说明结果。
- **问题与风险**：发现的缺陷、未覆盖场景、环境限制。
- **最终状态**：PASS / FAIL / BLOCKED。

只有实际执行并满足要求的测试才能标记 PASS。

CI/CD 未执行、测试环境缺失或测试被跳过时，必须明确说明，不得推断为通过。

## 7. 规范维护

本规范采用渐进式维护方式：

- 项目初始化时只配置必要测试工具和基本质量门禁。
- 新增重要功能时补充相关测试要求。
- 出现重复性缺陷时，将改进措施沉淀到测试规范。
- 项目复杂度提高后，再引入更完整的专项测试策略。
- 定期删除不再适用的规则，避免规范持续膨胀。

**最终目标：让软件测试成为可持续执行的开发习惯，而不是额外增加的一套形式化流程。**
